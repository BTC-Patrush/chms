# ADR-006 — Database roles and least privilege for CHMS-F001
Status: Accepted
Date: 2026-10-27
Context: [CHMS-F001](../../features/CHMS-F001/specification.md) needs a schema owner, a runtime application role and audit roles (ADR-005). The audit found that "M00 foundation/roles" in [migration-strategy.md](../../database/migration-strategy.md) does not say whether it means database roles or IAM roles; for F001 it means database roles. PostgreSQL 18 grants `CONNECT` and `TEMPORARY` on databases, and `EXECUTE` on functions, to `PUBLIC` by default ([privileges](https://www.postgresql.org/docs/18/ddl-priv.html), checked 2026-10-27).
Decision:
1. Roles:

| Role | Login | Purpose | Attributes |
|---|---|---|---|
| `chms_owner` | yes, operator use only | Owns schema `chms` and every object in it; runs migrations and bootstrap | `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS` |
| `chms_app` | yes | Runtime role for services and maintenance commands | `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`; not a member of any predefined role |
| `chms_audit_writer` | no | Owns `chms.audit_row_change()`; `INSERT` on `chms.audit_events` only | `NOLOGIN` |
| `chms_audit_reader` | no | `SELECT` on audit tables; granted only to authorized operator logins (POL-03) | `NOLOGIN` |

2. Database level: `REVOKE CONNECT, TEMPORARY ON DATABASE … FROM PUBLIC`; grant `CONNECT` explicitly to `chms_owner`, `chms_app` and named operator logins. No role except the owner gets `TEMPORARY`.
3. Schema level: all objects live in schema `chms`, owned by `chms_owner`. `USAGE` is granted to `chms_app`, `chms_audit_writer` and `chms_audit_reader`; `CREATE` to nobody else. `ALTER DEFAULT PRIVILEGES FOR ROLE chms_owner IN SCHEMA chms REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC`.
4. Table privileges for `chms_app` are column-level, as listed in [CHMS-F001 database design §5](../../database/CHMS-F001-database-design.md#5-role-and-privilege-matrix):
   - `id` is never insertable, because ids are generated by the database (ADR-001).
   - Identity columns are never updatable (ADR-003).
   - No `DELETE`, `TRUNCATE`, `REFERENCES`, `TRIGGER` or `MAINTAIN` on any table.
   - No privileges on audit tables.
5. Creating roles, setting role passwords and granting audit-reader membership are privileged operator actions that need explicit authorization (`CLAUDE.md`). They are run as a separate bootstrap step, not by routine migrations.
6. Test-only login roles and actor categories exist only in test clusters (POL-02).
7. The application is not exposed over HTTP during F001 (decision TD-10). These roles grant nothing to any web path.
Alternatives:
- One role for both migrations and runtime: simplest, but a compromised application could change schema, triggers and audit.
- Row-level security now: blocked until the trusted-actor decision (RR-07) has adversarial proof.
- A `NOLOGIN` owner with a separate migrator login using `SET ROLE`: stricter, but adds role-membership complexity that the migration tooling would need to support. It can be revisited.
Consequences:
- Separate credentials per role.
- An operator procedure for managing audit-reader membership.
- The role bootstrap script needs explicit human authorization to run.
Security impact (residual):
- `chms_app` can read every F001 row, because there is no RLS. Campus scope is enforced only in services, which is why F001 has no exposure.
- **Table locks.** `LOCK TABLE` allows any lock mode to roles with `MAINTAIN`, `UPDATE`, `DELETE` or `TRUNCATE` privileges "on the table", and only `ACCESS SHARE` to roles with `SELECT` ([LOCK](https://www.postgresql.org/docs/18/sql-lock.html), checked 2026-10-27). `chms_app` holds only **column-level** `INSERT` and `UPDATE` grants, so it is *expected* to be limited to `ACCESS SHARE`. Whether column-level grants count is unverified (TS-F001-31).
- **Row locks.** `chms_app` can still hold row locks through `UPDATE` or `SELECT … FOR UPDATE`. A compromised application could block archive and update operations for as long as its transaction stays open.
- **Self-set defaults.** `chms_app` can set defaults for itself with `ALTER ROLE chms_app SET …` ([ALTER ROLE](https://www.postgresql.org/docs/18/sql-alterrole.html)). This is relevant to ADR-005's actor setting; detection is in TS-F001-28.
- The owner and superusers remain trusted.
Verification (not executed): TS-F001-29 to TS-F001-31 in the [test matrix](../../features/CHMS-F001/test-matrix.md). Execution status: NOT RUN.
Approvers: Patrush (product owner), 2026-10-27. Accepted without amendment.
Errata (2026-10-27): E2. The "Self-set defaults" residual does not apply: PostgreSQL 18 denies `chms_app` `ALTER ROLE chms_app SET chms....` (`42501`, CP-09). A session-level `SET` remains possible (ADR-005). The decision is unchanged.
